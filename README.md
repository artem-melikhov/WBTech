# Отгрузки без простоев — прогнозирование логистических отгрузок

Решение кейса **«Отгрузки без простоев»** хакатона **WildHack** (организатор — ООО «РВБ», Wildberries), платформа [WB Space](https://wbspace.wb.ru/competitions/otgruzki-bez-prostoev).

**Результат: топ-30 в общем лидерборде (~1000 участников), совсем немного не хватило до призовой десятки.**

---

## 1. Постановка задачи

**Бизнес-контекст**: логистика маркетплейса — управление автопарком складов. Зная заранее, сколько товара будет отгружено со склада в ближайшие часы, можно точнее планировать количество машин: меньше простоев (машины ждут зря) и меньше дефицита транспорта (товару некуда грузиться).

**ML-задача**: регрессия временного ряда. По историческому движению товаров через склады нужно предсказать объём отгрузок (`target_1h`) для каждой пары (маршрут, момент времени) в тестовой выборке.

**Данные**:
- Train: 4.63М строк — 1000 маршрутов × 4630 получасовых снимков, период 28 июля – 1 ноября 2025.
- Test: 8000 строк — те же 1000 маршрутов × 8 шагов (1 ноября, 11:00–14:30, суббота).
- Зазор между train и test — ровно 30 минут.
- В train есть 6 колонок `status_*` (промежуточные этапы движения товара по складу-конвейеру), в test их **нет** — это ключевое ограничение задачи.

**Метрика**: `WAPE + |Relative Bias|` — сумма взвешенной абсолютной ошибки и штрафа за систематическое смещение прогноза.

Полное описание задачи и данных — [`docs/ОПИСАНИЕ_ЗАДАЧИ.md`](docs/ОПИСАНИЕ_ЗАДАЧИ.md).

---

## 2. Ключевой инсайт

Самые предсказательные признаки (`status_1…6`) отражают конвейер обработки товара на складе и отсутствуют в тесте. Анализ показал, что `status_1 → status_2 → status_3 → target_1h` — это последовательный конвейер с лагами:

```
status_1(t) ──[30–60 мин]──► status_2(t') ──[30–60 мин]──► status_3(t'') ──[30 мин]──► target_1h
```

Лаг `status_3 → target_1h` равен ровно **30 минутам на 100% маршрутов** — это значит, что `status_3` из последней строки train (10:30) напрямую предсказывает первую тестовую точку (11:00). Это наблюдение стало основой самых удачных фичей во всех последующих экспериментах.

Подробный разбор данных — [`docs/insights.md`](docs/insights.md) и [`notebooks/EDA.ipynb`](notebooks/EDA.ipynb).

## 3. Подход и валидация

**Схема валидации** — rolling-origin time-series CV, имитирующая условия теста: cutoff в 10:30 каждой из нескольких субботних дат train, прогноз на 8 шагов вперёд (11:00–14:30), метрика усредняется по фолдам. При инференсе `status_*` после cutoff не используются — только то, что доступно на момент cutoff.

**Постобработка**, общая для всех моделей:
1. `clamp(0)` — отрицательные прогнозы обрезаются;
2. калибровка `|Relative Bias|`: домножение прогнозов на `ratio = Σy_val / Σŷ_val` (бесплатно обнуляет смещение);
3. округление до целых.

## 4. Эксперименты

| # | Эксперимент | Идея | WAPE+RBias (CV) |
|---|---|---|---|
| — | Baseline: последнее известное значение | наивный прогноз | 0.516 |
| — | Baseline: среднее по маршруту | лучший простой бейзлайн | **0.382** |
| — | Baseline: среднее route+час / route+dow+час | усложнение бейзлайна ухудшает результат | 0.401 / 0.409 |
| [03](experiments/03_lgbm_conveyor) | LightGBM + конвейерные фичи | единая модель, `horizon` как признак, лаги `status_1/2/3` от cutoff | заложил ключевые фичи для всех следующих экспериментов |
| [04](experiments/04_lgbm_per_horizon) | LightGBM, 8 моделей по горизонтам | отдельная модель на каждый из 8 шагов прогноза вместо одной общей | **0.3269** |
| [05](experiments/05_catboost) | CatBoost + ordered target encoding | нативная обработка `route_id` как категории | не доведён до результата (заготовка) |
| [06](experiments/06_optuna_tuning) | Optuna-тюнинг LightGBM | автоматический подбор гиперпараметров, 100 трайлов | 0.3249 на быстром 1-фолдовом objective |
| [09](experiments/09_normalization) | Нормализация по маршруту | таргет и лаги делятся на `route_mean`, чтобы убрать 20-кратный разброс масштабов маршрутов | **0.3267** |

Лучшая локальная валидация (~0.327) получена комбинацией идей экспериментов 4, 6 и 9: раздельные модели по горизонтам, конвейерные лаговые фичи, нормализация по маршруту и тюнинг гиперпараметров. Итоговая посылка на платформу собиралась на основе этих наработок.

## 5. Структура репозитория

```
.
├── README.md
├── docs/
│   ├── ОПИСАНИЕ_ЗАДАЧИ.md   # полное описание задачи, данных и метрики
│   └── insights.md          # находки по данным, накопленные по ходу работы
├── notebooks/
│   └── EDA.ipynb             # разведочный анализ данных
└── experiments/
    ├── 03_lgbm_conveyor/       # LightGBM + конвейерные status-фичи
    ├── 04_lgbm_per_horizon/    # 8 отдельных моделей по горизонтам
    ├── 05_catboost/            # CatBoost (не завершён)
    ├── 06_optuna_tuning/       # тюнинг гиперпараметров
    └── 09_normalization/       # нормализация по маршруту
```

Номера экспериментов не идут подряд — это соответствует нумерации из исходного плана эксперимента; часть гипотез (ансамблирование, кластеризация маршрутов, нейросети, двухстадийная модель) осталась неопробованной из-за ограничения по времени хакатона.

## 6. Как воспроизвести

Данные (`train_solo_track.parquet`, `test_solo_track.parquet`) в репозиторий не включены — ожидаются в папке `Data/` в корне проекта (см. `.gitignore`). Ноутбуки самодостаточны: открыть нужный файл из `experiments/` и выполнить последовательно.

Основные зависимости: `pandas`, `numpy`, `lightgbm`, `catboost`, `optuna`, `matplotlib`.
